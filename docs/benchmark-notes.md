# Benchmark notes

Files: `data/benchmark_problems/benchmarks.json` (generated by `scripts/build_benchmarks.py`), evaluated by `scripts/evaluate_benchmarks.py`.

## What is measured
- 7 positive pairs. Each query is a small hand-authored structured problem. Each positive target is a seed system that a human would call a fair structural analog.
- Negative lookalikes: for each query, one hand-written entry that reuses the query's vocabulary and roles but breaks the structure (for example a sensor that reports to a display instead of a controller). In addition, an adversarial rewired control is generated from each positive (same nodes, roles and edge count, edge targets rotated).
- Metrics: whether the positive outranks every negative, positive score margin, rank of the positive among 69 candidates, hit@k for the set of acceptable analogs, MRR for the primary target, and a lexical-only baseline (rank by the semantic component alone).

## Honest caveats
- **Tuning and evaluation overlap.** The matcher, the seed knowledge base and the benchmarks were written by the same author in the same project. Component formulas and weights (25/25/20/15/10/5) were fixed before the first benchmark run, but the benchmark was read while building the matcher. One benchmark choice was changed after the first run: the primary target of `bq_gauge_control` was first `trans_ramp_metering`, and the lookalike (which is nearly the same wiring as the query) outranked it. The target was changed to `econ_taylor_rule`, whose skeleton (measure, signal, control, act on process) fits the query better, and `trans_ramp_metering` stays in the acceptable set. This is a correction of a poorly chosen pair, not an independent result.
- **Lookalike redesign after seeing results.** The first `bq_gauge_control` lookalike (a sensor reporting to a logbook) shared five of six edges with the query, so it correctly outranked the remote analog. A near copy of the query is a closer analog, not a negative lookalike. It was replaced by a same-words, wrong-wiring entry (`la_gauge_scrambled`). The first version is documented here because the change favours the matcher.
- **Fair metadata for lookalikes.** Lookalikes copy the declared behaviours, dynamics and constraint tags of the positive target, so a missing-metadata penalty cannot separate them. Only structure and wording differ. The engine additionally ignores a declared `negative_feedback` or `positive_feedback` tag when the graph has no loop of that polarity (this check also found one inconsistent seed entry, the token bucket, which was corrected).
- **n = 7.** No statistical claim can be made from seven pairs. Treat the numbers as regression checks.
- Positives were chosen by human judgement of structural similarity. There is no external ground truth.
- The margin on `bq_gauge_control` is small (a few points). The lookalike there differs from the query by one edge.
- Same-domain lookalikes are scored without the cross-domain filter so they can compete.

## Held-out perception set (phase 5)
Files: `data/benchmark_problems/perception_heldout.json`, evaluated by `python3 scripts/evaluate_perception.py`.

- 25 short free-text problems from many domains, 104 hand-labelled entities, written using vocabulary that is not in `ROLE_LEXICON` or `SYNONYMS`. The set was committed with the baseline numbers (commit a61c827) before any perception change, and was not edited afterwards to fit the code.
- Perception changes made after the baseline: morphology and head-noun fallback, a role index learned from seed knowledge labels, and verb-cue context inference marked as inference with lower confidence. An optional AI classifier exists but is off by default and is not part of these numbers.

| Metric | Before | After |
|---|---|---|
| detection_recall | 0.788 | 0.846 |
| role_coverage (entities with any role) | 0.220 | 0.440 |
| role_accuracy (correct role) | 0.115 | 0.404 |
| precision_when_assigned | 1.000 | 0.857 |

- **Caveat: the author wrote both the set and the code.** With n = 25 problems and 104 entities this is a regression check, not an accuracy estimate. The real-world rate on other people's text is unknown.
- Precision fell from 1.000 to 0.857 because more roles are now assigned. About 1 in 7 assigned roles is wrong. Roughly 60% of gold entities still get a wrong role or none.
- Still not detected: entities without a determiner, and compounds whose head is unknown but whose modifier is a lexicon word (for example "load shedder").
- Unchanged by this work: `evaluate_benchmarks.py` MRR 0.9286 (lexical-only baseline 0.2566), roller top score about 36.5, knowledge base still 66 seed systems. The roller score was not tuned.
- `run_demo.py` changed only the limitations text in `data/demo/sample_investigation.json` (the text now describes the new perception). `docs/sample-discovery-report.md` is unchanged.

## Roller demo score and placeholder parameters
- The flagship roller demo (`python3 scripts/run_demo.py`) ranks "Human core temperature regulation" first with a score of about 36.5 out of 100 (roughly 37). This is a low absolute number. Scores are heuristic and only meaningful as a ranking, and the weights sum over six components that rarely all match for distant domains.
- Results were not tuned to look better. The best cross-domain score for the roller problem is about 36.5/100 and is reported as is. Weights, lexicon and seed graphs were not adjusted to raise it, and any future change that does so must be recorded here.
- The roller experiment uses placeholder material parameters (for example for copper). They are not measured values. The seeded rolling simulation is illustrative: a "supported" result means the proposed controller beat the baseline inside that toy model, not in a real mill.

## Dependency lock file
`frontend/package-lock.json` cannot be generated here because `npm install` is blocked (no registry access). Builds are therefore not reproducible until someone runs `npm install` on a networked machine and commits the lock file.
