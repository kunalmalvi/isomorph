# Gated self-improving loop: evidence log, versioned learned config, regression gate (v1)

The change adds a learning loop that uses only recorded user evidence (role corrections, hypothesis decisions, mapping edits, experiment outcomes). From that evidence it builds a lexicon overlay and conditional priors. Each candidate becomes a new registry version. It is activated only if no frozen-set metric drops, and every propose, accept, reject and rollback goes to an append-only audit log. The loop is wired into the app (`/learning` routes, `learn` CLI command, Learning page, orchestrator perception), and opt-in Gaussian-copula correlations are added to Monte Carlo sampling. Docs state the limits plainly: no accuracy gain is claimed, and the gate is blind to priors. `data/benchmark_problems` is untouched and the runtime is stdlib only.

Watch for: (1) evidence ids can collide when the CLI and the server share one home (likely); (2) learned priors have no consumer in the app's orchestrator path (confirmed, disclosed in docs); (3) repeated cycles on unchanged evidence keep creating rejected versions (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The loop is layered cleanly. `EvidenceLog` validates and appends, builders turn evidence into a candidate config, and `ModelRegistry.propose` runs the gate and activates or rejects. Learning reads the frozen held-out and tuning files only in the gate and in a leak guard that quarantines overlapping terms. Experiment outcomes are hard-pinned to `simulation` evidence, so nothing can be recorded as real-world.

The only place learning changes behavior in the product today is the perception lexicon overlay, applied by the orchestrator when the provider is local. Conditional priors are learned, versioned and gated, but only `pipeline.investigate` consumes them. The app never calls it, so a prior accepted through the UI changes nothing. The gate cannot see priors either, so those versions are accepted as "not sensitive".

Evidence is held in memory per process and loaded once. The server and the CLI each open their own `App`, so they diverge on ids and visibility when used together.

<summary>Issues (4)</summary>

1. **Evidence id collision across processes (likely)** — `EvidenceLog` reads the JSONL once and assigns `ev-{len+1}` in memory. A CLI `learn correct` while the server runs yields duplicate ids, and the server never sees the CLI's events. Re-read the file under a file lock before each append, or use a monotonic id derived from the file.
2. **Learned priors never applied in the app (confirmed)** — `learned_prior` is called only from `pipeline.investigate`. The orchestrator uses `derive_concepts` directly. Apply priors in the orchestrator's concept ordering, or hide priors from the Learning page and status until they are consumed.
3. **Rejected candidates repeat each cycle (likely)** — a rejected candidate leaves the evidence unchanged, so the next `cycle()` builds the same candidate, reruns the gate and stores another rejected version. Skip when the candidate matches the last rejected config for the same evidence ids.
4. **Weak distinct-run rule (confirmed)** — a correction without `run_id` counts as its own vote, so one caller repeating a request satisfies the 2-run rule. Acceptable for a local single-user app; require a run id if the evidence must resist one actor.

## Evidence ids and the CLI/server split

`EvidenceLog.__init__` loads `evidence.jsonl` once and `append` numbers the next event from the in-memory length. `cmd_learn` opens a full `App` (and so a second `LearningService`) on the same home as a running server. If both append, two events can share an id, for example `ev-7`. The builders key votes and the "latest decision wins" map on `ev["id"]` when there is no run id. A collision therefore silently merges or overwrites evidence, and the server's `status()` and `cycle()` ignore anything the CLI wrote until restart. This undermines the "auditable" requirement for a feature whose docs advertise the CLI path. The registry has the milder form of the same problem: its audit `seq` comes from `len(self.audit())` and it relies on the in-process `RLock`. A reload-before-append under an OS file lock fixes both.

## Priors: learned, gated, not consumed

```
feedback / outcome -> propose_priors -> registry (gate: not sensitive) -> active.config.priors
                                                                      \-> learned_prior() -> pipeline.investigate only
orchestrator._hypothesis stages -> derive_concepts / select_distinct   (no prior lookup)
```

`set_annotation` records feedback with `{"query_domain": ...}` conditions, and the cycle turns three matching decisions into a prior. Nothing in `services/orchestrator.py` calls it, and `experiment_outcome` evidence is never recorded by any app code path, only by the loop's own API and tests. The docs disclose that only `investigate` applies priors. The user-visible effect is still that the Learning page can show "N priors" in the active version while no run is affected. The verdict is NEEDS_CHANGES mainly because the request was a working self-improving loop. Either wiring priors into the orchestrator or labelling them as inert in the UI would close it. Separately, `pipeline.investigate` calls `memory.prior_adjustment(c.concept_type)` without the conditions argument added in this diff, so the conditional form of `MemoryStore` is unused too.

## Gate behavior on repeated and unchanged candidates

`LearningService.cycle` compares the candidate only to the active config. After a rejection the evidence is unchanged, so the same candidate is rebuilt and sent through `ModelRegistry.propose`. Each call allocates a new version id, runs two full metric evaluations (perception, held-out retrieval, tuning benchmarks) and logs a propose and reject pair. `status()["pending"]["would_change"]` stays true forever, so the UI keeps inviting the user to run a cycle that will be rejected again. Deduplicating against the most recent rejected version with the same evidence ids is enough.

## Lexicon overlay and leak guard

The leak guard rejects a term if its head word is the head of any held-out phrase or if the term appears as a word sequence in held-out or benchmark query text. This is deliberately conservative and is reported as `heldout_overlap` with a reason, which is the right shape for an audit trail. The guard runs only in `propose_lexicon`. `ModelRegistry.propose` accepts any validated config, so a hand-written config via the API of the registry bypasses it, but no HTTP route accepts a raw config, so this is not reachable from the app today. The overlay never overrides a head word the built-in lexicon already resolves, which keeps learned terms from displacing known behavior. A learned source carries 0.6 confidence, above head-noun (0.5) and below the lexicon (0.7), and the inference text tells the user it is a guess and names the config version.

## Security and trust posture

A standalone correction with no `run_id` counts as its own distinct vote (`ev["id"]` fallback), so one caller can post a term twice without a run and satisfy the 2-run support rule. That only needs repeating the same request, so the "2 distinct runs" rule is not a real defence against a single user. This matters only if the evidence is meant to resist one actor, and for a local single-user app it is acceptable.

## Test coverage

Covered: evidence validation, vote rules (support, agreement, conflict), the leak guard, registry accept, reject, rollback and activate, gate rejection on any metric drop, app end to end through the HTTP server and CLI in a temp home, and copula sampling. Not tested: two `LearningService` instances on one directory (the id collision), repeated `cycle()` after a rejection, priors affecting an orchestrator run, and the Learning page in a real browser (docs mark it UNVERIFIED).
